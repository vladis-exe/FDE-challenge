# Model comparison (V4): which model runs the conversation

**Decision: Haiku 5.5 for the fast tier (understanding each message, writing each reply);
Sonnet 5.5 for the smart tier (the recruiter summary).** This is the configuration the engine
ships with.

**Status: provisional, one repeat per configuration.** The plan was 3 full-suite repeats each.
Repeats 2 and 3 stopped when the Anthropic account ran out of credits, and those runs were
discarded. The numbers below come from one clean full run of each, on the same engine
(`screening/` at `8d4ad12`, harness at `cb63291`) and the same scenarios. Re-run the repeats with the commands at the end once credits
are topped up.

## Recommendation: Haiku 5.5 for the conversation, Sonnet 5.5 for the summary

1. **Sonnet bought no quality on anything we measure.** Both configurations got every
   outcome right, so the same candidates were qualified, disqualified and sent to review.
   Both kept every message within the limits and answered in the candidate's language.
   Neither model decides an outcome: code does (DECISIONS D3). That narrows the model's job
   to reading messy messages and phrasing replies, and Haiku already does that at the
   ceiling of these 20 scenarios.
2. **Sonnet made an error Haiku didn't.** Two candidates gave a first name, were asked
   for a surname and answered "ramirez soto". Sonnet then stored only the surname as the
   full name (scenarios 09 and 19). Haiku merged the two answers correctly in the same
   scenarios. A bigger model isn't automatically safer on extraction.
3. **6.4× the cost and slower for the candidate.** Extract and compose cost 19× more on
   Sonnet, and each message takes about 0.5 s longer at the median. On WhatsApp, the
   candidate feels that wait on every turn. Sonnet's one advantage is fewer first drafts
   regenerated by the reply guard (9% vs 14%), and the guard already catches those for Haiku
   (100% rule compliance either way).
4. **Sonnet stays where its quality is read by a person: the recruiter summary.** It is one
   call per conversation, and it writes the note a recruiter reads before deciding. The
   eval doesn't score summary quality, so we have no evidence yet that Haiku's summaries
   would be as good. It is also the largest part of A's cost (68%), so it is the next thing
   to test (see below).

## Limits of this evidence

- **One repeat.** LLM behavior varies from run to run. In separate single-scenario runs
  on Haiku, "eso da igual no? prefiero no decirlo" was misread as an opt-out once in 3 runs
  (scenario 17; the engine lane has the
  [transcript](findings/optout-misread-17_unresolved_location_madrid.md)). An earlier full
  run of B, under an older version of the harness, passed 20/20, so Sonnet's surname slip is
  intermittent too. The three repeats per configuration are what will tell steady
  differences from noise.
- **20 synthetic scenarios.** They cover every outcome and the hard cases in the spec,
  but the candidates are simulated. Real WhatsApp traffic will contain cases they don't.
- **Some faults don't depend on the model.** These go to the engine lane, not to a
  model choice:
  - the read-back loop ("Notes for other lanes" in `docs/coordination/status/evals.md`);
  - merging a surname answer into the first name in code, not in the model;
  - reading "de NL" (where the license was issued) as the candidate's location.

  Fixing them in code makes the conversation more robust than a bigger model would.

## What would change the decision

- If the repeats show Haiku failing a scenario that Sonnet passes consistently, look at
  that failure first. If a prompt or code fix can't close it, use Sonnet for extraction
  only. Extraction is where comprehension matters; compose is phrasing, which the guard
  enforces.
- At 10,000 a week, test **C: Haiku for all three tiers.** The summary is 68% of A's
  cost, and C would cost about $0.002 per conversation. That needs a summary-quality check
  first: an LLM judge against the final record, or a recruiter reading 20 of them side by
  side.

## Reproduce

```bash
uv run python -m evals.run --name v4-haiku --fast-model claude-haiku-5-5    # A (3×)
uv run python -m evals.run --name v4-sonnet --fast-model claude-sonnet-5-5  # B (3×)
uv run python -m evals.compare --config "A=evals/runs/<a1>,<a2>,<a3>" --config "B=evals/runs/<b1>,<b2>,<b3>"
```

A full run takes about 4 minutes. The candidate simulator adds about $0.30 per run on top of
the engine cost above.
